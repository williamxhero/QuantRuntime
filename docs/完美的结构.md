# 完美的结构：以 Strategy Workspace 连接 Discovery 与多 Formal Backend

下一步最重要的，不是再增加一个研究库，也不是指定某个交易引擎成为唯一标准，而是建立一个真正中立、版本化、可复现的 **Strategy Workspace**。

它将当前容易固化为：

```text
Qlib Discovery → 某一个 Formal 引擎 → Apex Research
```

的流程升级为：

```text
                         Strategy Workspace
              package / capability / snapshot / lineage
                                  │
                    ┌─────────────┴─────────────┐
                    ▼                           ▼
             Discovery Adapters           Formal Backends
          Qlib / 自定义研究器 / 无       ApexTrade / LEAN / NautilusTrader
                    │                           │
                    └─────────────┬─────────────┘
                                  ▼
                      Research / Evidence Control
```

其中：

- Discovery 层负责提出候选：模型、信号、规则、参数或策略实现。
- Formal 层负责正式执行：行情事件、订单、成交、持仓、账户、保证金和市场规则。
- Strategy Workspace 负责描述、连接、选择、冻结和记录，而不是成为第四个交易引擎。
- Apex Research 是研究控制层的一种实现，不垄断 Strategy Package，也不绑定特定 Discovery 或 Formal backend。

这套结构的目标不是让所有引擎变得一样，而是在保留各自原生能力的前提下，使策略能够被统一管理、确定性路由、复现实验并进行跨引擎验证。

## 一、核心原则

### 1. Strategy Workspace 是中立控制面

Strategy Workspace 自身不负责撮合，也不负责模拟账户。它提供的是跨层治理能力：

- Strategy Package 的身份、版本和完整性。
- 参数 schema 与运行参数冻结。
- 策略需求和 backend 能力的声明。
- Discovery 与 Formal adapter 的注册和选择。
- MarketHub 数据请求的标准化。
- MarketHub 逻辑快照的创建、定位和复用，以及按配置选择是否在本地物化。
- 运行拓扑、运行 manifest 与证据血缘。
- 跨 backend 的核心结果规范化。
- engine-native 产物的完整保留。

### 2. Formal 层是多引擎运行层

Formal 层同时容纳：

```text
Formal Layer
├─ ApexTrade Backend
├─ LEAN Backend
└─ NautilusTrader Backend
```

三者都是一等公民：

- 没有默认主引擎。
- 没有固定 reference engine。
- 没有固定 fallback engine。
- 都通过相同的 backend contract 声明能力、接受运行请求并产出证据。
- 可以单独运行，也可以在同一冻结快照上分别运行并比较结果。

“平等”不代表能力完全相同，也不要求抹平各引擎的特色。Capability Resolver 应保留差异，并根据策略需求选择合格 backend。

### 3. 领域执行能力由 Formal backend 兑现

必须明确区分两种能力：

| 能力类型 | 主要实现者 |
|---|---|
| 策略包、版本、参数 schema | Strategy Workspace |
| capability 声明、匹配与路由 | Strategy Workspace |
| MarketHub adapter、逻辑快照、可选本地物化与血缘 | Strategy Workspace |
| 结果归一化、证据归档 | Strategy Workspace |
| 因子、模型、候选参数生成 | Discovery backend |
| 行情事件、订单、撤单、成交 | Formal backend |
| 现金、持仓、组合和账户状态 | Formal backend |
| 做空、保证金、逐日结算和换月 | Formal backend |
| 实盘 broker 对账 | Formal backend |

Workspace 可以验证某个引擎是否具备 `futures.margin`，但不能通过声明让一个不具备该能力的引擎突然获得正确的保证金语义。

### 4. 单次 Formal run 的状态只能属于一个引擎

一次正式运行中的以下状态必须由同一个 backend 从头到尾负责：

- 订单生命周期。
- 撮合与成交时序。
- 现金和持仓。
- 保证金和强平。
- 费用、滑点和结算。
- 合约换月与 broker reconciliation。

禁止在一次运行中让一个引擎维护持仓、另一个引擎补算保证金，再回到第一个引擎继续撮合。这会产生两套账户状态和无法解释的结果。

如果需要切换 backend，必须以同一冻结输入从运行起点重新开始。如果需要比较 backend，则创建多个彼此独立的 Formal run。

## 二、为什么需要 Strategy Workspace

现有量化工作流很容易隐含以下固定假设：

- 每个策略都必须先经过 Qlib。
- 每个策略最终都由某一个固定引擎执行。
- 策略输出只能是 `target_weight`。
- 所有策略都类似股票横截面 Top-K。
- 新增策略需要修改 Runtime 或 Research 核心代码。
- 数据在每个阶段被重新查询，输入无法严格复现。
- 不同引擎运行结果只有最终收益率，没有完整配置和输入血缘。

这些假设不适合通用研究：

- 传统 CTA 可以跳过 Discovery。
- 机器学习选股适合 Qlib，但不应被 Qlib 绑定。
- 日内突破是事件驱动策略。
- 做市策略输出订单意图，而不是每日权重。
- 跨期套利涉及多条腿和组合状态。
- 同一策略可能需要在 ApexTrade、LEAN、NautilusTrader 上独立验证。

Strategy Workspace 的价值不在于重新实现三个引擎已有的功能，而在于建立它们都不负责的中立合同：策略身份、能力需求、实现映射、冻结输入、运行血缘和可比较证据。

## 四、Strategy Package v1

每个策略都是独立、版本化、内容可寻址的 Strategy Package。示例：

```toml
schema = "quant-research.strategy-package.v1"
strategy_id = "futures.time-series-breakout"
revision = 1
display_name = "期货时间序列突破"
parameter_schema = "parameters.schema.json"

[pipeline]
discovery = "optional"
formal = "required"

[requirements]
asset_classes = ["futures"]
frequencies = ["1m", "1d"]
capabilities = [
  "market.cn.futures",
  "position.short",
  "portfolio.multi_instrument",
  "futures.contract_roll",
  "futures.margin",
  "session.night",
  "strategy.persistent_state"
]
decision_intents = ["target_contracts", "order"]

[implementations.discovery]
qlib = "discovery/qlib/pipeline.yaml"

[implementations.formal]
apextrade = "formal/apextrade/strategy.apx"
lean = "formal/lean/BreakoutAlgorithm.cs"
nautilus = "formal/nautilus/strategy.py:BreakoutStrategy"

[dependencies]
markethub_contract = "v2"
calendar = "cn-futures-v1"
```

Strategy Package 至少冻结：

- `strategy_id`、revision、显示名称。
- Package schema 版本。
- 参数 schema 和默认值边界。
- Discovery 是否必需、可选或禁止。
- Formal 是否必需。
- 所需资产、频率、事件和市场语义。
- 支持的 canonical decision 类型。
- 各 Discovery/Formal backend 的实现入口。
- 原生依赖和 engine API 版本。
- 策略包内容 hash。

实现入口是显式映射，不代表策略代码可以自动跨引擎执行。LEAN 实现不会因为存在 ApexTrade adapter 就自动变成 `.apx`；要么提供对应实现，要么使用经过验证的中间表示和编译器。

## 五、Runtime Capability v1

Strategy Package 声明 `requirements`，每个 backend 声明 `provides`。Capability Resolver 只做确定性匹配，不猜测、不静默降级。

一个 backend profile 可以包含：

```yaml
backend_id: nautilus
adapter_version: 1.0.0
engine_version: 1.x
provides:
  - market.cn.equity
  - market.cn.futures
  - event.intraday
  - portfolio.multi_instrument
  - position.short
  - order.market
  - order.limit
  - strategy.persistent_state
conditional:
  futures.margin:
    policy: cn-futures-v1
```

Capability 应描述可验证的语义，而不只是宽泛标签。建议至少覆盖：

- 资产：股票、ETF、期货及具体市场。
- 数据：tick、order book、分钟、日线、公司行动。
- 策略模型：batch、event-driven、stateful、多标的。
- 决策：目标权重、目标仓位、目标合约、订单、组合腿。
- 订单：market、limit、stop、cancel/replace。
- 市场规则：T+1、涨跌停、整手、停牌。
- 期货规则：乘数、保证金、逐日结算、平今、夜盘、换月和临近交割约束。
- 运行模式：backtest、paper、live。
- 证据：逐单记录、逐日账户、引擎原生日志和确定性重放。

当 backend 缺少必需能力时，默认必须 fail closed。只有运行策略显式允许时，才可以选择另一个合格 backend 并从头创建新的 run；任何 backend 都没有默认 fallback 地位。

## 六、Formal backend 的四种选择模式

### 1. 指定模式

```yaml
formal:
  mode: pinned
  backend: lean
```

用户或实验协议明确指定 backend。能力不足时直接失败，不自动换引擎。

### 2. 能力匹配模式

```yaml
formal:
  mode: capability_match
  selection_policy: deterministic
```

Resolver 先得到全部合格 backend，再根据显式规则选择，例如：

- 实盘 broker 支持。
- 市场语义完整度。
- 可重放性。
- 性能和资源预算。
- 已通过的 conformance suite。

如果选择规则不能唯一决定结果，应要求调用方指定，而不是依赖注册顺序。

### 3. 多引擎验证模式

```yaml
formal:
  mode: comparison
  backends: [apextrade, lean, nautilus]
```

三个 backend 使用同一个 Strategy Package、参数和冻结快照，分别创建独立 run。差异本身就是研究证据，不预设任何引擎是真值。

### 4. 一致性门模式

```yaml
formal:
  mode: agreement_gate
  backends: [apextrade, lean, nautilus]
  minimum_agreement: 2
```

一致性门不要求逐笔结果完全相同，而应对预先声明的结论进行比较，例如：

- 扣除成本后收益是否为正。
- 最大回撤是否低于阈值。
- 收益方向和主要持仓阶段是否一致。
- 参数扰动后结论是否稳定。
- 差异能否由成交模型、费用、换月或交易日规则解释。

## 七、MarketHub Adapter、逻辑快照与可选本地物化

MarketHub adapter 负责把远端 MarketHub 数据能力转换成 Workspace 的标准数据请求。这里的 Snapshot 首先是一次运行所使用数据的**稳定身份和查询合同**，不必等同于一份本地数据副本。

Workspace 必须始终生成 Snapshot Manifest，但调用方可以选择：

- `materialized`：把数据物化为不可变的本地副本，以文件内容 hash 保证强复现。
- `reference`：只保存指向 MarketHub 的逻辑引用和规范化查询，假定上游历史数据不会变化，不保存权威本地副本。

推荐流程：

```text
MarketHub
    │ 标准化查询
    ▼
Snapshot Resolver
    ├─ Reference Snapshot ───────────────┐
    │   只保存 manifest                  │
    │                                    ▼
    └─ Materialized Snapshot ────── Discovery / Formal Backend
        保存不可变本地数据及分区 hash
```

Discovery 和多个 Formal backend 应引用同一个 `snapshot_id`。具体数据可以由 backend 通过 MarketHub adapter 直接读取，也可以从已物化的本地副本读取。

### Snapshot 配置

```toml
[data]
adapter = "markethub"

# materialized | reference
snapshot_mode = "reference"

# verified_immutable | assumed_immutable | mutable
trust_policy = "assumed_immutable"

# none | ephemeral | persistent
local_cache = "none"
```

两个配置维度彼此独立：

- `snapshot_mode` 决定权威数据身份是本地物化内容，还是远端逻辑引用。
- `local_cache` 决定运行过程中是否允许生成可删除或可复用的本地缓存。

缓存模式含义：

- `none`：直接从 MarketHub 读取，不保留本地行情数据。
- `ephemeral`：允许为某个引擎生成临时文件或格式转换结果，运行结束后可以删除。
- `persistent`：持久保存转换结果以加速后续运行，但缓存仍不自动成为权威快照。

某些 Formal backend 不能直接查询 MarketHub，必须先生成引擎要求的数据文件。这种情况下可以使用 `snapshot_mode = "reference"` 与 `local_cache = "ephemeral"`：运行输入的权威身份仍是 MarketHub reference，落地文件只是可重建的适配产物。

### Reference Snapshot Manifest

```yaml
schema: quant-research.market-snapshot-ref.v1
snapshot_id: sha256:...
mode: reference
trust_policy: assumed_immutable
source:
  adapter: markethub
  endpoint_contract: v2
  data_revision: null
query:
  instruments: [CFFEX.IF.*]
  start: 2020-01-01
  end: 2025-12-31
  frequency: 1m
  adjustment: none
calendar: cn-futures-v1
contract_mapping: dominant-contract-v2
resolved_at: 2026-08-23T10:00:00+08:00
```

Reference snapshot 的 `snapshot_id` 至少由规范化查询、MarketHub endpoint contract、schema、交易日历、复权规则、合约映射和可获得的数据 revision 共同决定。如果 MarketHub 没有提供 revision、ETag 或内容 hash，则必须记录 `trust_policy: assumed_immutable`，表示复现性依赖“上游数据永不变化”这一显式假设，而不是已经得到内容级验证。

### Materialized Snapshot Manifest

```yaml
schema: quant-research.market-snapshot.v1
snapshot_id: sha256:...
mode: materialized
source_snapshot_ref: sha256:...
partitions:
  - path: bars/year=2020/part-000.parquet
    sha256: ...
```

Materialized snapshot 的 `snapshot_id` 必须包含实际文件内容 hash。创建后不可原地修改；上游补数、修订、复权规则或合约映射变化时，应创建新 snapshot。

### 共同规则

- 每次 run 必须记录 `snapshot_id` 和 `snapshot_mode`，不能只记录日期范围。
- 完全相同的 reference 请求优先复用现有 manifest；是否重新读取远端数据由 cache 和 backend 策略决定。
- Discovery 产生的特征、标签和模型属于派生产物，必须通过自己的 hash 指回 source snapshot。
- Formal backend 必须记录实际读取方式、adapter 版本和数据转换器版本。
- Engine-specific 转换产物必须记录输出 hash；在 `ephemeral` 模式下，即使文件已删除，也应保留转换 manifest。
- 多 backend 比较必须使用同一个逻辑 snapshot；不能各自构造不同的复权、交易日或连续合约映射。
- Reference 模式接受“上游数据若被静默修改，历史运行可能无法内容级复现”的风险，不能把这种假设描述成已验证的不可变性。
- 本地物化和缓存都只是 MarketHub 远端数据的消费方式，不意味着在本机另建一套 MarketHub 服务。

该设计让调用方可以在复现强度、磁盘占用和读取成本之间做明确选择：默认可以信任 MarketHub 而不保存本地数据，同时仍保留完整的数据查询身份和运行血缘。

## 八、Canonical DecisionIntent 的边界

Canonical DecisionIntent 用于跨层交换可移植的策略意图，但不应强迫所有引擎放弃原生 API。

建议的联合类型包括：

```text
TargetWeightIntent
TargetPositionIntent
TargetContractsIntent
TargetNotionalIntent
OrderIntent
CancelIntent
SpreadIntent
```

例如：

```json
{
  "type": "target_contracts",
  "instrument": "CFFEX.IF.202609",
  "target_contracts": -2,
  "decision_time": "2026-08-23T14:55:00+08:00"
}
```

它适合用于：

- Discovery 向 Formal 交付目标或订单意图。
- 多 backend 对相同离线决策流进行重放。
- 记录可解释、可审计的策略决策。

它不应侵入：

- backend 内部的订单状态机。
- 引擎原生事件回调。
- 账户、撮合和保证金模型。
- broker-specific 执行语义。

对于完全 event-driven、formal-only 的策略，可以只声明 engine-native implementation，而不要求所有内部决策都经过 canonical intent。统一边界，不统一引擎内部实现。

## 九、资产与市场规则

市场规则需要拥有中立的能力名称和版本，但真正执行仍由 Formal backend 负责。

需要覆盖：

- 股票 T+1、涨跌停、整手、停牌和公司行动。
- ETF 与股票的交易规则差异。
- 期货合约乘数和最小变动价位。
- 多空方向、保证金和逐日结算。
- 日盘、夜盘和交易日归属。
- 主力/连续合约映射与实际合约执行。
- 换月策略。
- 按金额、按手、开仓、平仓和平今的费用差异。
- 价格限制和临近交割约束。

Workspace 负责声明所需规则版本、检查 backend 是否通过对应 conformance suite，并把实际使用的 policy 写入 run manifest。不能在 Workspace 中暗自实现一套通用撮合器来填补 backend 的能力缺口。

## 十、通用运行拓扑

Workspace 不应固定为 `Qlib → NautilusTrader`，而应支持：

```text
discovery + formal
formal-only
multiple-discovery + formal
discovery + multiple-formal
formal A/B/C comparison
```

示例：

### 股票机器学习策略

```text
Qlib Discovery
      ↓
Strategy Candidate
      ↓
指定或匹配一个 Formal backend
```

### 传统期货 CTA

```text
Strategy Package
      ↓
跳过 Discovery
      ↓
ApexTrade / LEAN / NautilusTrader
```

### 跨引擎正式验证

```text
同一个 Strategy Package
同一组冻结参数
同一个 Market Snapshot
      ├─ ApexTrade Formal Run
      ├─ LEAN Formal Run
      └─ Nautilus Formal Run
```

## 十一、Research 控制层

Apex Research 不应假设一定存在 Qlib candidate，也不应假设 Formal run 一定来自某个固定引擎。它应该通过 Workspace 的公共合同管理：

- 参数空间。
- walk-forward。
- purged cross-validation。
- 开发集、OOS 和挑战集。
- 多目标优化。
- 稳健性和敏感性。
- 成本与滑点情景。
- 策略容量。
- 运行预算和提前停止。
- 跨运行归因。
- 多引擎差异分析。
- 候选晋级。
- 最终证据与决定。

Apex Research 只是 Research Controller 的一个实现。其他研究系统也可以消费同一个 Strategy Package、Snapshot Manifest、Run Manifest 和 Result Contract。

## 十二、运行证据与结果合同

不能为了跨引擎比较而丢弃 engine-native 细节。结果应分为两层：

### Canonical result

- 收益和风险指标。
- 资金曲线。
- 标准化持仓时间线。
- 标准化成交摘要。
- 费用、滑点和换手率。
- 数据、策略、参数、adapter 和引擎版本。
- warning、能力降级和不可比项。

### Engine-native evidence

- 原始订单和成交日志。
- 引擎原生账户状态。
- 原生配置和运行日志。
- broker/reality model、撮合模型和费用模型。
- engine-specific diagnostic artifacts。

跨引擎结论必须能追溯到两层证据。Canonical result 用于比较，engine-native evidence 用于解释差异。

## 十三、明确的非目标

Strategy Workspace v1 不应：

- 成为第四个撮合或交易引擎。
- 指定 ApexTrade、LEAN 或 NautilusTrader 为永久主引擎。
- 把任何一个引擎固定为 fallback 或真值。
- 在同一次 run 中拼接多个引擎的账户状态。
- 为追求统一而压缩到三个引擎的最低共同能力。
- 假设一种实现可以自动转换成另一种引擎的策略代码。
- 在 capability 不满足时静默忽略做空、保证金、夜盘等语义。
- 把 MarketHub 查询结果当作可变缓存而不记录内容 hash。

## 十四、推荐实施顺序

1. 编写 `Strategy Package v1`、`Runtime Capability v1`、`Snapshot Manifest v1` 和 `Run Manifest v1`。
2. 建立真正中立的 `strategy-workspace-core`，不依赖任何 Formal engine。
3. 实现 MarketHub adapter、逻辑 Snapshot Manifest，以及 `reference/materialized` 和本地缓存策略。
4. 定义统一的 Formal Backend Interface 和 capability profile。
5. 为 ApexTrade、LEAN、NautilusTrader 分别建立平级 adapter 骨架。
6. 将当前股票动量策略提取为第一个 Strategy Package，避免策略逻辑留在 Runtime 核心。
7. 支持 `formal-only`，用期货时间序列突破作为第二个差异化样本。
8. 以同一市场快照运行可用的多个 backend，建立 conformance 和差异解释机制。
9. 在确有跨层交换需求的地方引入 `DecisionIntent v2`，保留现有合同的向后兼容。
10. 改造 Apex Research，使其读取运行拓扑和 backend 集合，而不是硬编码 Qlib 或某个 Formal engine。
11. 最后扩展自动选择和一致性门；在基础合同稳定前，不把复杂调度作为第一目标。

实施顺序可以因现有代码成熟度而先完成某个 adapter，但这种工程顺序不得演变成架构优先级。

## 十五、验收标准

### 策略独立性

新增一种完全不同的股票或期货策略时，只新增 Strategy Package 和对应实现，不修改 MarketHub、Workspace core、Formal adapter core 或 Apex Research core。

### 引擎平权

- 调用方可以显式选择 ApexTrade、LEAN 或 NautilusTrader。
- Resolver 不使用隐式注册顺序决定引擎。
- 任一引擎能力不足时均采用相同的 fail-closed 行为。
- 多引擎比较不预设 reference backend。

### 状态完整性

每个 Formal run 的订单、成交、账户、保证金和持仓由一个 backend 完整负责，不发生跨引擎状态拼接。

### 数据可复现

- Discovery 和 Formal run 能复用同一个 `snapshot_id`。
- 多个 Formal backend 能消费同一逻辑输入，并记录各自的数据适配方式。
- `materialized` 模式可通过内容 hash 强复现；`reference` 模式明确记录对 MarketHub 不变性的信任策略。
- 不保存本地行情时，仍保留规范化查询、schema、日历、合约映射、adapter 版本和运行血缘。

### 证据可追溯

任意研究结论都能追溯到：

```text
Strategy Package hash
+ Parameters hash
+ Market Snapshot identity/hash
+ Discovery artifact hash（如有）
+ Formal adapter/version
+ Engine/version/configuration
+ Result and native evidence hash
```

### 能力诚实

不支持的市场语义必须在运行前失败，不能通过默认值、忽略规则或跨引擎拼接伪装成支持。

## 最终定义

> Strategy Workspace 是连接 Discovery 与 Formal 层的中立控制面。它负责 Strategy Package、capability negotiation、MarketHub 快照复用、backend 编排、运行血缘和证据合同；策略的订单、成交、账户、保证金及市场规则由被选中的 Formal backend 原生实现。

> ApexTrade、LEAN 和 NautilusTrader 是 Formal 层中平等的一等公民。它们可以被指定、按能力选择或在同一冻结输入上独立运行，但没有任何一个被固定为主引擎、真值或后备引擎。

当新增策略不再要求修改平台核心、同一策略能在不同 Formal backend 上以同一快照独立验证，并且所有差异都有完整证据可以解释时，这套结构才真正从“特定工作流”升级为“通用量化研究平台”。
